## 0. 評価の受け止め — 覆すもの / 受け入れるもの

レビューをコードベースと突き合わせて事実確認した。**指摘は概ね正確**であり、
感情的に反論するのではなく「測定で覆せるもの」と「ポジショニングとして
受け入れるもの」を分離する。

### 受け入れる(戦わない)

| 指摘 | 判断 |
|---|---|
| 「推論性能を上げる基盤ではない」「RAG品質・tool useを改善しない」 | **その通り。** hersona は人格レイヤーであり推論基盤ではない。README に「What hersona is / is not」を明記して過大期待を自ら断つ方が信頼される(→ P2-1) |
| 「小規模なら手書き system prompt で十分」 | **部分的にその通り。** 単一ペルソナ・固定運用なら手書きが最短。hersona が勝つのは「複数ペルソナの切替」「強度ダイヤル」「conflict 検出」「維持率の測定」が要る時 — この境界を比較表で明示する(→ P2-1) |
| 「採用実績が弱い(6 stars)」 | 短期で覆せない。`docs/IMPROVEMENT_PLAN.md` の認知施策の管轄。本計画では「外部が検証できる状態を作る」ことに集中する |

### 覆す(測定と実装で反証する)

| 指摘 | 反証の武器 |
|---|---|
| 「人格維持・token量の定量比較がない」(過大評価耐性 4/10 の主因) | **hersona には決定的採点器 `measure_intensity` が既にある**(語尾一致60% + 口癖密度40%、LLM 不要で再現可能)。レビュアー自身が書いた検証プロトコルをそのまま `hersona bench` として製品化する(→ P1-1) |
| 「README 208属性 / About 89属性の不整合」 | **事実で、しかも悪化している**: 現在 実体 345 / README 208 / About 89 の3つの数字が併存。単一ソース(`tests/catalog_counts.py`)から README を CI 検証する仕組みで再発を構造的に殺す(→ P0-1) |
| 「`hersona update` に署名検証がない」 | 事実(64MB 上限 + パストラバーサル対策のみ、`hersona/core/update.py`)。ハッシュマニフェスト検証 + PyPI Trusted Publishing + ビルド来歴 attestation で SLSA 方向へ(→ P2-2) |
| 「リリース運用に粗さ」 | semver ロールバックは CHANGELOG に既に正直に記録済み(隠していない点はむしろ強み)。リリースチェックリストの機械化で再発防止(→ P3-1) |

## 1. 中心戦略: 「唯一の測定可能なペルソナ層」を名乗れる状態にする

レビューの最終評価が 5/10 に沈む根本原因は 1 つ —
**主張(人格が崩れない)と証拠(なし)のギャップ**。

hersona の競合(手書きプロンプト / .cursorrules / 独自YAML)は
どれも「人格維持率」を測る手段を持たない。hersona だけが
`measure_intensity` / `verify_intensity` / `intensity_baseline` という
決定的・再現可能な採点器を同梱している。つまり:

> **「ベンチマークがない」という最大の弱点は、裏返せば
> 「ベンチマークを標準装備した唯一のペルソナ管理ツール」になれる最短の機会。**

レビュアーが提示した検証手順(10〜20シナリオ / あり・なし比較 /
口調維持率・品質・token量)を、そのまま `hersona bench` コマンドと
`docs/BENCHMARKS.md` として実装・公開する。外部が「試すなら検証方法」を
実行しようとしたとき、その手順が既に製品に同梱されている状態を作る。

## 2. 改善バックログ(優先度順)

### P0 — 即日〜今週(信頼の出血を止める)

**P0-1. 属性数の単一ソース化 + ドリフト CI ゲート**

- 現状: 実体 345(personality 42 / speech 140 / archetype 66 / visual 46 / hobby 51)、
  README EN/JA は 208 表記が各8箇所以上、GitHub About は 89。
- 対策:
  1. README EN/JA の数値を全て 345 に更新(即日)。GitHub About も更新。
  2. `scripts/check_readme_counts.py`(新規): `tests/catalog_counts.py` を単一ソースに、
     README EN/JA 内の属性数表記(合計・カテゴリ別)を正規表現で照合。CI に追加。
     `build_site.py --check` と同じ「生成物ドリフトを CI で殺す」既存パターンの横展開。
  3. About は API 経由で CI 検証できないため、リリースチェックリスト(P3-1)に組み込む。

**P0-2. token コスト表の公開(測定済み・最速の定量データ)**

- 注入ブロックの token 数は決定的に測れる(LLM 不要)。全属性 × 強度3段階の
  注入 token 数を `build_site.py` と同様のスクリプトで生成し、
  `docs/BENCHMARKS.md` の第1節として公開。
- 「token増加が許容範囲か」というレビュアーの成功条件に、導入前に答えられる状態にする。

### P1 — 2〜4週(反証の本丸)

**P1-1. `hersona bench` — ペルソナ維持ベンチマークハーネス**

- 設計(レビュアーの検証プロトコルを製品化):
  - `benchmarks/scenarios/*.yaml`: 10〜20 の会話シナリオ(質問列 + 期待タスク)。
    CC0 で同梱し、外部が同じ条件で再実行可能にする。
  - `hersona bench run --blend <names...> --weight <w> --provider <openai|anthropic|ollama|none>`:
    各シナリオを「hersona 注入あり / なし(素) / 手書き相当プロンプト」の3条件で実行し、
    ターンごとに `measure_intensity` で採点。
  - 出力メトリクス: **人格維持率**(強度バンド内ターン比率)、**維持率の減衰曲線**
    (ターン経過での低下 = 「長時間会話で崩れるか」への直接回答)、**token コスト**、
    (任意)LLM-judge による品質スコア。
  - `--provider none` なら記録済み応答での決定的リプレイ(CI 可能)。
- 結果は `docs/BENCHMARKS.md` に、条件・モデル・日付・再現コマンド込みで公開する。
  **良い結果だけでなく悪い結果も載せる**(例: 「strong 強度は品質を X% 落とす」
  が出たらそれ自体が「正直なドキュメント」として信頼を作る + 改善課題になる)。

**P1-2. README「What hersona is / is not」+ 競合比較表**

- is not: 推論基盤ではない / RAG・tool use を改善しない / 単一固定ペルソナなら手書きで十分。
- is: 複数ペルソナの規格化・切替 / 強度ダイヤル / conflict 検出 / **維持率の測定** /
  5形式 export。「hersona を使うべき時・使わなくていい時」のディシジョンガイドを表で明示。
- レビューの「代替手段」リスト(手書き / .cursorrules / LangGraph / 独自YAML)を
  そのまま比較軸として引き受ける。LangGraph 等とは競合ではなく
  「export で載せる先」であることも明記(既に `langchain_system_message` がある)。

### P2 — 1〜2ヶ月(供給網と実務信頼)

**P2-1. `hersona update` のハッシュ検証**

- リリース時に `attributes/` アーカイブの SHA-256 マニフェスト
  (`checksums.json`)を GitHub Release アセットとして発行。
- `update.py` はダウンロード後にマニフェスト照合(既定 ON、
  `--no-verify` でオプトアウト)。マニフェスト自体はタグ付きリリース経由で取得。
- 併せて `SECURITY.md` を新設: 脅威モデル(何を守り何を守らないか)、
  既存対策(64MB 上限 / パストラバーサル拒否)、報告窓口を明記。
  「セキュリティは最低限」という指摘には、**最低限の中身を文書で示す**のが第一歩。

**P2-2. PyPI Trusted Publishing + ビルド来歴**

- `publish.yml` を PyPI Trusted Publishing(OIDC)へ移行し、
  `actions/attest-build-provenance` でビルド来歴 attestation を付与。
  SLSA 方向への実質的な一歩で、コスト小。

### P3 — 継続(運用の粗さ対策)

**P3-1. リリースチェックリストの機械化**

- `docs/RELEASE_CHECKLIST.md` + タグ駆動リリースの dry-run ステップ。
  項目: CHANGELOG 節の繰り上げ / README・About の属性数 / `build_site.py` /
  スキルの SemVer / PyPI publish の検証。semver ロールバック再発をプロセスで防ぐ。

**P3-2. 採用実績づくり(IMPROVEMENT_PLAN と合流)**

- ベンチ結果 + デモサイト(30秒体験、実装済み)+ X 広報ボット(hersona 自身が
  デモになる構造、`docs/IMPROVEMENT_PLAN.md` §戦略1)を三点セットで発信。
- `USED_BY.md` / Discussions 有効化 / good first issue の整備で
  「外部からの検証や利用者コミュニティが薄い」への受け皿を先に作る。

## 5. やらないこと(スコープ規律)

- **実務エージェント基盤(RAG / tool use / memory)への拡張はしない。**
  レビューの正しい指摘を無理に覆そうとして製品を薄めるのが最悪手。
  「キャラプロンプト管理ツール」という評は、**測定機能を伴えば**
  「persona layer as code」という独自カテゴリの言い換えになる。
- 有料ベンチ環境が必要な大規模 LLM 比較はしない(決定的採点 + 小規模 LLM-judge まで)。
- スター数を直接追う施策は本計画の外(`docs/IMPROVEMENT_PLAN.md` 管轄)。
